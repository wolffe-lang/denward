# Capacity and inventory budget

The supplied root-filesystem size is 5,738,460 KiB, approximately 5.47 GiB allocated, including the base system. This is a small migration for the reported Mac receiver capacity, and restarting an interrupted SSH transfer from zero is acceptable at this scale. It is not an exact archive size: excluded base/cache files reduce selection, headers add overhead, sparse logical size can exceed allocated space and separate mounts need their own inventory. The tool must still compute selected bytes/entries and check actual receiver/target space before use.

For plaintext archive length A and the selected ordinary age profile, ciphertext length is `C = header_bytes + 16 + A + 16*max(1,ceil(A/65536))`. Use C, not A, for receiver retention and ciphertext cache. Reserve a new complete object, a retained previous object and `max(10% of C, 1 GiB)` headroom, plus filesystem costs. If C were about 5.5 GiB, this is roughly 12 GiB plus metadata, comfortably within the reported receiver allowance. Inspect, not this estimate, decides actual admission. Restore separately reserves reconstructed data, preimages and its complete ciphertext cache.

First-release inventory/sort metadata stays entirely in memory within the 256 MiB total process ceiling. No plaintext or encrypted on-disk inventory spool is enabled. The old million-entry proposal is withdrawn. The actual representation must be measured at several entry counts and name/map sizes, with fixed overhead, bytes per entry, worst-case bounds and peak RSS recorded from a small parent. Set the release entry bound only from that measurement with headroom; inspect reports its count and refuses by name above the bound. Until the actual representation is measured, its nonzero admission bound is unqualified; enabling inventory must be blocked by `inventory_budget_unqualified`. The current scaffold already refuses every data operation as unimplemented. A modest byte total is not proof of a modest entry count.

Large-input qualification remains substantially above this installation: 1 GiB, 8 GiB and 32 GiB generated archive/encryption streams under fixed memory limits; the 32 GiB row also crosses the old shared-reader 16 GiB aggregate limit. Do not commit huge fixtures or buffer these streams. Disk/SSH retained-generation and restore rows use explicit separately reserved capacities, and must preserve runner free-space floors; a streaming hash-sink test is not a real-store durability claim. Run memory-growth/fuzz/large-stream legs only in bounded Linux environments, not on a personal Mac. Missing or out-of-budget rows are not passes.
