# Manifest v1

The manifest is data, never code. It uses UTF-8 JSON Lines: one object per LF-terminated line, no BOM, duplicate keys, comments, floats, executable expressions, unknown fields or trailing non-record data. All strings must be shortest-form scalar UTF-8. Integers are canonical decimal JSON integers within signed 64-bit range; negative values are allowed only for time seconds. Object field order on input is immaterial; the canonical writer uses the field order below, no insignificant spaces, JSON escapes for quotes/backslashes/control characters and one final LF per record. The largest encoded line is 1 MiB; large sparse maps use separate extent records rather than one unbounded array.

The first record is `header`, followed by exactly three path-sorted `control` records, `selection`/`exclusion` records, sorted `object` records, path-sorted `file` records with their consecutive `extent` records, and one final `end` record. Unknown schema or required feature rejects before target writes. Features is an array of distinct understood feature identifiers; the initial feature set is empty. Parsing never evaluates a language expression or imports a module.

Exact record keys, in canonical order:

- `header`: `record` = `header`, `schema` = 1, `features` = [], `archive_profile` = `pax-objects-v1`, `source_release` and `source_manifest` (lowercase SHA-256), `tool_version` (nonempty bounded UTF-8 string).
- `control`: `record`, `archive_path` (exactly one each of `control/accounts`, `control/config-defaults`, `control/installed`), `length` (nonnegative), `sha256` (lowercase SHA-256). These bind the control payloads without a self-hash for `control/manifest`.
- `selection`: `record`, `path`, `kind` (`home`, `config`, `local-data`, `audit`, `accounts`), `mount_identity` (a non-secret stable identity string), `baseline_sha256` (lowercase SHA-256 or empty when not applicable). Only a selection record may use empty path to describe the logical root; it grants no recursive extraction authority.
- `exclusion`: `record`, `path`, `reason` (a fixed documented reason identifier), `explicit` (boolean).
- `object`: `record`, `id` (lowercase SHA-256), `length` (nonnegative), `archive_path` = `objects/` followed by the same id. Duplicate ids with different bytes/lengths reject. All referenced data objects must exist and every physical object must be referenced.
- `file`: `record`, `path`, `type` (`file`, `dir`, `symlink`, `hardlink`, `deleted`), `mode` (0–4095), `uid` and `gid` (0–4294967295), `user` and `group` (resolvable names or empty), `length`, `sha256`, `object`, `link_group`, `target`, `atime_sec`, `atime_nsec`, `mtime_sec`, `mtime_nsec`, `ctime_sec`, `ctime_nsec`, `birthtime_present`, `birthtime_sec`, `birthtime_nsec`, `sparse` (boolean), `extent_count`. Every key is required. Times have nanoseconds 0–999999999. Ctime/birthtime are observed-only. `target` is symlink text or an in-set regular-file path for a hard link. Inapplicable strings are empty, numeric values zero and booleans false; they are never omitted or null.
- `extent`: `record`, `path`, `offset`, `length`, `object`, `object_offset`. Nonnegative offsets, positive length, ordered non-overlapping logical ranges bounded by that file's declared length. Object references and ranges must resolve. No arithmetic overflow or implied allocation outside declared extents is accepted.
- `end`: `record`, `file_count`, `object_count`, `extent_count`, `logical_bytes`, `stored_object_bytes`. These independently recompute exactly. No record follows `end`.

Regular nonsparse files require exactly one object reference of matching length and no extent records; regular sparse files require extent records and no direct object reference, with logical SHA-256 including holes. Empty files still have a digest and zero-length object. Directories require zero length and empty digest/object/target. Symlink text is bounded UTF-8 data and its object digest binds its exact bytes; archive extraction never follows it. Hard-link targets name a declared regular file, without chains, with matching effective metadata/link group; metadata mapping is validated before applying. Deleted records preserve old configuration deletion intent, carry no object/digest/target and are never a blanket permission to remove new base files.

Paths are normalized relative UTF-8 paths, at most 4096 bytes, without NUL, controls, backslash, empty/dot/dot-dot components or a trailing slash. Unsupported real names are refused by name, not renamed. Symlink text is separate: absolute, dangling and dot-dot text can be preserved as data, but never traversed for writes. Duplicate logical paths, conflicting ancestors, undeclared extents/references, unexplained physical members and missing control files reject.

Semantic account/password contents, original default configuration and installed-package reports are restricted control payloads, never secret manifest values. They use the same strict JSON Lines encoding. `control/accounts` has exactly three database records in order passwd/group/shadow, with keys `database`, `present` (boolean), `object` (data-object digest or empty when absent); original database bytes stay in the referenced opaque objects. Missing shadow is represented as absent, not an invented password. `control/config-defaults` has path-sorted records with keys `path`, `state` (`file` or `absent`), `object` (digest or empty); original default bytes are referenced objects, independently checked against the old image inventory. `control/installed` starts with `record` = `header`, `schema` = 1, `database_available` (boolean), then sorted `package` records (`record`, `name`, `version`, `arch`, `reason`) and path-sorted `unmanaged` records (`record`, `path`, `sha256`, `action` = `review`), followed by `end` (`record`, `package_count`, `unmanaged_count`). These reports never execute install hooks. The account/configuration merger validates these schemas before use. All records and strings remain bounded; unknown fields reject.

This manifest does not embed its enclosing archive's digest. The complete stored-file receipt is detached; see stream-v1 and stores-v1.

No reader/writer is implemented at this milestone. Frozen schema fixtures and a future independent parser checker must precede actual backup emission. Any schema change after a released v1 fixture requires explicit compatibility handling, not rewriting the fixture.
